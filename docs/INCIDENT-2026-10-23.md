# Ingestion connection closures, 2026-10-23

## Evidence

The collector reported `connection closed before message completed` around 00:35 UTC. At inspection, Podman reported 35 collector restarts, zero database restarts, and no container OOM kills. The host still had approximately 27 GB free RAM and 735 GB free disk, but DolphinDB's own `maxMemSize` was only 2 GB.

The database log at the same time contained:

```text
00:35:12  Out of memory, BlockFileOutputStream failed to alloc memory and will retry.
00:35:15  Failed to append to the TSDB cache engine ... Out of memory
00:35:16  The job ... was cancelled ... std::bad_alloc
00:35:20  Console output exception: std::bad_alloc
```

TSDB compaction also repeatedly reported out-of-memory errors. This establishes database memory exhaustion during the failures; it is not evidence of Binance rejecting the connection. The transport exception alone cannot determine whether an individual batch committed.

Before maintenance, subscription counters showed:

- `compute`: `failedMsgCount=0`.
- `archiveRaw`: `failedMsgCount=1494`, with an out-of-memory append error.
- `archiveFactors`: `failedMsgCount=1086`, with an out-of-memory append error.

These are reported failure counters, not a reconciled count of unique missing events. A subsequent successful collector run does not repair these historical failures.

## Changes

- Raised the persistent `maxMemSize` setting to **8 GB**. `license()` reported an 8 GB/node allowance. The live limit was first changed with `setMaxMemSize(8)` and verified through `getClusterPerf()`; the database was then restarted with the updated file during maintenance.
- Paused the collector and Grafana while recovering the database and validating changes. Named volumes and historical tables were retained. Live snapshots during downtime are not backfilled by this POC.
- Kept the no-blind-write-retry policy: repeating an ambiguous append can duplicate records and bias stateful factors.

## Additional timestamp defect uncovered during verification

In the actual container, at host UTC `2026-10-23 00:42:42`, DolphinDB returned:

```text
now()         = 2026.10.23T00:42:42
gmtime(now()) = 2026.10.22T16:42:42
```

The previous conversion was therefore shifting an already-UTC clock by eight hours. Server-generated `ingestTs`/`computeTs`, freshness queries and date filters were affected; Rust's receive epoch and Binance event/transaction epochs were not generated through this conversion.

The code now uses `now()`/`now(true)` with the existing `TZ=UTC` container setting. A collector startup check compares server time against Rust's UTC clock. The smoke test now derives its fixture event time from Python's independent Unix epoch and checks the server clock separately. Earlier same-clock fixture checks did not establish absolute UTC correctness in this container. Old timing records are preserved and must not be treated as corrected latency measurements.

## Follow-up

At 00:46:49 UTC after deployment, `getClusterPerf()` reported an 8 GB limit. The rebuilt collector had zero restarts; all three newly created subscriptions had zero failed messages and zero queue depth, with over 15,000 events processed. These are post-restart counters, not proof of recovery of the earlier failures. Rust tests, Clippy, formatting, the independent-clock smoke test, and all ten Grafana panel queries passed.

A live BTCUSDT event showed `eventTs=00:46:49.015`, `receiveTs=00:46:49.038259409`, `ingestTs=00:46:49.045746102`, and `computeTs=00:46:49.051905745`, all on 2026-10-23 UTC. Use periods after approximately 00:46:04 UTC for corrected server-generated timing fields. The stack was left running.

Monitor memory, compaction warnings, query ranges, and changes in subscriber failure counters during a longer run. An 8 GB limit adds headroom, not an unlimited-capacity guarantee. Failed archival writes and ambiguous batches need separate reconciliation against retained stream logs and event IDs; this maintenance does not claim exactly-once recovery or complete historical data.
